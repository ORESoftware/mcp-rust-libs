## Fleet findings enforced by the shared auditor

The audit ratchet detects:

- handwritten JSON-RPC and hard-coded obsolete protocol revisions;
- pre-1.0 `rmcp` compatibility debt;
- Streamable HTTP below the `rmcp` 1.4.0 DNS-rebinding security floor unless an equivalent reviewed Host-validation patch is documented;
- `wait_with_output`, `Command::output`, and whole-body reqwest sinks;
- stdout writes in production Rust;
- credentialed HTTP clients without redirect denial, exact-host policy, or `no_proxy`;
- Streamable HTTP without an obvious bearer or Host boundary;
- permissive tool input structs without closed runtime schemas;
- mutating tools without an independent runtime gate, target-bound confirmation, idempotency, or dry-run signal;
- serialized MCP results without an obvious final output ceiling;
- mutable GitHub Action pins, implicit workflow permissions, and persisted checkout credentials;
- missing lockfiles, CI, tests, and real-binary initialize/tools lifecycle tests.

Static findings are review signals, not proof. False positives require a repository-local, evidence-backed exception instead of weakening the fleet rule globally.

## SDK and protocol baseline

The current signed upstream `rmcp` release is 3.0.1. It is a breaking SDK release that adds the 2026-07-28 release-candidate lifecycle while retaining legacy serving paths. Fleet policy is lifecycle-aware rather than “latest major equals secure”:

- new SDK migrations normally target `rmcp` 3.0.1 and test the intended lifecycle explicitly;
- reviewed 2.2.x stdio servers may remain on the stable `2025-11-25` lifecycle until a breaking migration is justified;
- Streamable HTTP must meet the known 1.4.0 security floor or carry an equivalent reviewed Host-validation patch;
- custom compatibility endpoints must be explicitly bounded, tested, and tracked as exceptions.

## Physical-control standard

Drone and laser MCP servers require a stricter boundary than ordinary diagnostics:

1. The MCP process cannot replace downstream authorization, geofences, hardware interlocks, or human supervision.
2. Every credentialed upstream origin is exact-host allowlisted; redirects and ambient proxies are disabled.
3. Remote cleartext service networks require a separate explicit override and may never bypass the allowlist.
4. Mutations default off and require confirmations bound to the selected resource and action.
5. Runtime validation enforces finite coordinates, route and duration limits, UUID form, free-form JSON ceilings, and final output ceilings.
6. Real-binary lifecycle tests prove initialization, tool discovery, unknown-field rejection, default-disabled mutations, and secret-free diagnostics.
7. CI ratchets these invariants with immutable actions and read-only default permissions.
