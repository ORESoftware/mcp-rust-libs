## Fleet findings now enforced by the shared auditor

The audit ratchet now detects:

- handwritten JSON-RPC and pre-3.x `rmcp` migration debt;
- hard-coded obsolete protocol revisions;
- `wait_with_output`, `Command::output`, and whole-body reqwest sinks;
- stdout writes in production Rust;
- credentialed HTTP clients without redirect denial, exact host policy, or `no_proxy`;
- Streamable HTTP without an obvious bearer or Host boundary;
- permissive tool input structs without `deny_unknown_fields`;
- mutating tools without an independent runtime gate, confirmation, idempotency, or dry-run signal;
- serialized MCP results without an obvious final output ceiling;
- mutable GitHub Action pins, implicit workflow permissions, and persisted checkout credentials;
- missing lockfiles, CI, tests, and real-binary initialize/tools lifecycle tests.

Static findings are review signals, not proof. False positives require a repository-local, evidence-backed exception rather than weakening the fleet rule globally.

## Physical-control standard

Drone and laser MCP servers require a stricter boundary than ordinary diagnostics:

1. The MCP process cannot replace downstream authorization, geofences, hardware interlocks, or human supervision.
2. Every credentialed upstream origin is exact-host allowlisted; redirects and ambient proxies are disabled.
3. Remote cleartext service networks require a separate explicit override and may never bypass the allowlist.
4. Mutations default off and require confirmations bound to the selected resource and action.
5. Runtime validation enforces finite coordinates, route and duration limits, UUID form, free-form JSON ceilings, and final output ceilings.
6. Real-binary stdio tests prove initialization, tool discovery, unknown-field rejection, default-disabled mutations, and secret-free stderr.
7. CI ratchets these invariants and uses immutable actions with read-only default permissions.

## Protocol baseline

Production servers should negotiate the current final MCP revision, `2025-11-25`, and remain forward compatible. The `2026-07-28` revision is treated as a draft/next-version compatibility target, not something to force fleet-wide before its SDK and interoperability behavior is reviewed.
